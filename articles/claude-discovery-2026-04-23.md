# Claude Code 今日の発見 — 2026-04-23

「自動化したい」という欲求と、「でも結局人間が見ないと不安」という本音。その狭間で、興味深い実験がいくつも動き始めている。

---

## 16台のClaudeが寝ずにCコンパイラを書いた話

Anthropic研究員のNicholas Carlini氏が、ちょっとした実験をした。Claude Codeのインスタンスを16台並列で走らせ、Linuxカーネルをコンパイルできる本格的なCコンパイラを作らせたのだ。結果、10万行のRustコードが生成され、Linux 6.9のビルドに成功した。API費用は約2万ドル、会話数は約2,000回。

仕掛けはシンプルだ。各エージェントは無限ループで新しいClaude Code会話を起動し続け、Gitを同期プリミティブとして使う。人間は一切介在しない。テストが唯一の品質管理手段になるため、GCCを「予言機」として参照し、出力が一致するかどうかで正しさを判定する。

興味深いのは、限界も正直に報告されている点だ。x86の16ビットコード生成ではOpusモデルが苦戦し、最適化効率はGCC（-O0）にも劣る。LLMは高レベルの設計には強いが、低レベル最適化はまだ人間の領域らしい。広告クリエイティブの大量生成でも、同様の「並列エージェント＋テスト駆動」アプローチは使えそうだが、品質基準をどう定量化するかが鍵になる。

[IceYao's Blog](https://www.iceyao.com.cn/2026/04/15/claude-parallel-agents-c-compiler/)

## 「前提知識ゼロ」でリリースを乗り切ったTVerのiOSエンジニア

動画配信サービスTVerのiOSエンジニア福島氏が、途中参画した大規模プロジェクトをClaude Codeで乗り切った事例が公開された。プロジェクト固有の仕様をほとんど把握しないまま、不具合解消フェーズに投入されたという状況だ。

武器にしたのは3つのカスタムスキル。`/analyze-and-create-issues`で不具合を分析しGitHub Issueを生成、`/implement-issue`でIssueに基づく実装とビルド確認、`/create-pr`でPR作成。これらを同様に途中参画した他メンバーにも共有し、属人化を防いだ。

ポイントは「AIに任せた」ではなく「AIを使えるようにチームで標準化した」点だ。新メンバーのオンボーディング工数をスキルで吸収するアプローチは、代理店業務で頻繁に発生するプロジェクト間の人員移動にも応用できる。

[TVer Tech Blog](https://techblog.tver.co.jp/entry/claude-code-use)

## 毎朝7時に11個のAI自動化が勝手に動き出す

アソビュー株式会社CPOの横峯樹氏がnoteで公開した記事が、派手さのない実用性で注目を集めている。「30分でアプリを作りました」系のデモではなく、毎朝7時に自動起動し、起床してSlackを開くと必要な情報が揃っている——そんな地味な自動化を11個作ったという話だ。

横峯氏はプロダクトマネージャーであり、ゴリゴリのエンジニアではない。それでもClaude Codeで「定着する仕組み」を構築できた点が示唆的だ。彼が強調するのは、デモ映えする一度きりの実装と、実務で継続利用できる自動化の間には大きな溝があるということ。定例レポートの下書き、Slackチャンネルの要約、社内データの定点観測といった「やればいいのに誰もやっていなかったこと」こそ、Claude Codeの本領かもしれない。

## Claude Code Routines——24時間働くエージェント基盤

4月14日、AnthropicがClaude Code Routinesをリサーチプレビューとして公開した。プロンプト、リポジトリ、コネクタ（Slack、Linear、GitHub等）を一度設定すれば、スケジュール、API呼び出し、GitHubイベントのいずれかをトリガーに自動実行される仕組みだ。

実用例として挙げられているのは、PRオープン時の自動レビュー、夜間のバックログ分類、デプロイ後のスモークテスト、週次のドキュメント乖離検出など。ただし現時点では監査証跡が不十分で、実行前の承認チェックポイントもない。規制業界での本番投入にはまだ早いが、「失敗しても取り返しがつくタスク」から始めるには十分だ。

マーケティングオペレーションで言えば、週次レポートの下書き生成、キャンペーン終了後の自動集計、広告アカウントの異常検知あたりが現実的な導入候補になる。

[Claude Code Routines Practical Guide](https://jangwook.net/en/blog/en/claude-code-routines-practical-guide-2026/)

## 「20%速くなった」と感じて、実際は19%遅くなっていた

Qiitaに投稿されたnogataka氏の記事が、AIツール活用の盲点を突いている。2025年7月のMETR研究を引用し、熟練開発者がAIツールを使った結果、主観的には「20%速くなった」と感じたが、客観的には19%遅くなっていたという事実を紹介している。

原因は「効率の幻想」だ。認知負荷が下がると時間の経過を短く感じるが、AIの出力をレビューし、微修正し、デバッグする時間は確実にかかっている。Stack Overflowの調査でも66%の開発者が「ほぼ正しいが完全ではないAI出力」を課題に挙げ、45%が「デバッグに時間がかかる」と回答している。

記事が提案するのは、「何をAIに任せるか」ではなく「人間とAIの協働をどう設計するか」という視点の転換だ。定型的で低リスクな業務はAIに、文脈依存的な判断は人間が——という切り分けと、静的解析→レビュー→テスト→ステージングの4段階ゲートの組み込みを推奨している。

[Qiita（nogataka）](https://qiita.com/nogataka/items/4960530673874672c626)

## qlaude——Telegram経由でClaude Codeを遠隔操作

コミュニティ発のツール「qlaude」が、ニッチだが実用的な問題を解決している。Claude Codeは便利だが、複数タスクを順番に処理したい場合や、途中で判断を求められた場合に人間が張り付いている必要がある。qlaudeはタスクキューとTelegramブリッジを追加し、スマートフォンから承認や選択肢の指定ができるようにした。

設計思想として「完全な自動化」ではなく「必要なときだけ人間が介入できる半自動化」を志向している点が興味深い。Claude Codeの透明性を損なわず、失敗モードを隠さないことを優先しているという。出張中や移動中でも長時間タスクを走らせておき、判断ポイントだけ通知を受けて対応する——そんなワークフローが可能になる。

[Medium（Agent Native）](https://agentnativedev.medium.com/qlaude-queue-based-claude-code-automation-with-telegram-control-778de887f465)

## GitHubコミットの4%がClaude Code製になった

DEV Communityの記事が、ひとつの指標を報告している。Claude CodeがGitHub上の全コミットの約4%を占めるようになったという。「誤差の範囲」ではなく「構造的変化」だと筆者は主張する。

記事が強調するのは、「速度」よりも「レビュー品質」が本当の価値だという点だ。Claude Codeを「フィードバックが必要なジュニア開発者」として扱うチームは、良いコードを生産している。逆に、仕様なしで大規模リファクタを任せたり、複雑なビジネスロジックを検証なしで自動化したりするチームは、技術的負債を積み上げている。

勝ちパターンとして紹介されているのは、プロンプトを「設計ドキュメント」のように扱うアプローチだ。受け入れ基準、制約、非目標、エージェントが確認すべき計画を明示し、コードに触れる前に合意を取る。広告運用の自動化でも、「何を自動化するか」より「どこで人間が確認するか」の設計が成否を分けそうだ。

[DEV Community](https://dev.to/hamza_a_1dba9c327788c448f/claude-code-is-reshaping-software-engineering-in-2026-4ljf)

## Proプランから一瞬消えて、すぐ戻った騒動

4月21日、Anthropicが予告なくclaude.com/pricingを書き換え、Claude Codeを$20のProプランから削除して$100/$200のMaxプラン専用にした。数時間後、SNSでの反響を受けて元に戻った——これも予告なしに。

Head of Growthのツイートによれば「新規ユーザーの約2%を対象にした小規模テスト」で、既存ユーザーには影響なかったという。ただ、この出来事はClaude Codeの収益化モデルがまだ固まっていないことを示している。現在のProプランで使い続けられるかどうかは、今後も注視が必要だ。

[Zenn](https://zenn.dev/sktt_panda/articles/claude-code-pro-plan-removal-2026-04)
